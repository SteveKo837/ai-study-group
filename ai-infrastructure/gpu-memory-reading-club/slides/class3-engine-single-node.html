02

先給結論：兩家的哲學差異

這頁的判斷後面每一題都會驗證一次。先放在這裡，聽眾才有掛東西的鉤子。

SGLang

「結構化 LLM 程式」的執行引擎

第一性問題是：一個會分支、會重試、會反覆用同樣前綴與語法的 LLM 程式，怎麼跑得最快？

· DSL 描述執行圖

· radix tree 做前綴索引

· cache-aware 排程主動提高命中率

· jump-forward 跳過確定的 token

vLLM

「模型服務」的基礎設施

第一性問題是：任何模型、任何硬體、任何部署形態，怎麼都能穩定地服務起來？

· 模型／硬體後端覆蓋最廣

· KV connector、語法後端皆可插拔

· 路由與編排交給生態系

· V1 重寫把 CPU 開銷壓到最低

一句話：SGLang 在「前綴與語法重複」這條路上挖得深；vLLM 在「什麼都能跑」這個面上鋪得廣。不是誰比較好，是最佳化的目標函數不同。

地基①：所有問題的共同根源

先確認「敵人是誰」：第一堂的「<5% 之謎」，算到底是 0.34%。

每產一個 token（batch = 1）

搬（Bytes）

整份權重讀一遍 = 2N bytes

算（FLOPs）

每個參數一次乘加 = 2N FLOPs

算術強度 AI

2N ÷ 2N = 1 FLOP/Byte

H100 ridge point ≈ 296 FLOPs/Byte

算力利用率上限

1 ÷ 296

≈ 0.34 %

你買的 H100，99.7% 的算力在閒置。

卡越強，batch=1 越浪費（A100 是 0.6%）。

接下來每一個問題，本質上都是「這 99.7% 為什麼填不滿」的不同面向——兩家都在打這件事。

04

地基②：AI ≈ B，所以答案永遠是「把 batch 撐大撐滿」

搬：權重還是只讀「一遍」（2N bytes）　　算：2N × B FLOPs　　→　AI ≈ B

既然 ridge point ≈ 296，B 要拉到「幾百」GPU 才餵得飽。而 B 撐不大的每一個理由，就是後面每一個問題。

Llama-3-8B on H100：batch=1 ≈ 208 tok/s　→　batch=64 ≈ 13,000 tok/s（步時幾乎不變）

四個問題各自擋住 B 的哪一段

①

程式難平行

根本沒有那麼多請求同時進來——runtime 看不見可平行的分支

②

前綴重算

HBM 被浪費的 KV 佔住 → 放不下更多條；算力浪費在不必算的東西上

③

輸出不可控

每步的語法檢查是 CPU 上的序列工作 → 拖慢整批

④

CPU 成瓶頸

GPU 算完在等 CPU 決定下一步 → 有效 batch 再大也填不滿時間軸

把這張圖記住，後面就不會覺得是在背功能表——每個機制都在拆掉擋住 B 的一塊石頭。

對比①：vLLM 沒有對應物——而那是刻意的

SGLang

有一層語言

· sgl.gen / fork / select 描述執行圖

· runtime 看得見分支結構，主動批處理

· fork 的共享前綴直接餵給 radix tree

· 代價：要學一套 DSL、綁定這個 runtime

vLLM

只有 API

· Python LLM 類 + OpenAI 相容 server

· 平行化交給呼叫端（asyncio、批次提交）

· 或交給上層框架（LangChain、DSPy…）

· 好處：任何客戶端都能用，零學習成本

為什麼這不是「缺漏」？

因為兩家對「引擎的職責邊界」判斷不同。vLLM 認為「怎麼組織 LLM 程式」是應用層的事，引擎只該把單一請求服務好；SGLang 認為程式結構是效能資訊，不交給引擎就浪費了。

實務上：多數人把 SGLang 當純 server 用、從沒碰過 DSL——所以這一層在日常使用上常常是沒被啟用的器官。但它解釋了 SGLang 為什麼那麼在意前綴共享。

第一個對比就看到哲學差異：一家往上長出語言，一家往外接生態。後面三題會反覆看到這個分野。

②

要複用前綴，得先解決「KV cache 怎麼放」

複用的東西是 KV cache。但傳統做法是照 max_seq_len 連續預留一整塊——不知道會生成多長，只好照最壞情況要。結果多數請求只用到預留量的 20–30%，其餘是死重，HBM 放不下更多條（B 上不去），更別說跨請求共享。

KV cache 一個 token 多少？

2(K,V) × n_kv_heads × head_dim × n_layers × dtype

Llama-3-8B（GQA 8 heads、128 dim、32 層、fp16）＝ 128 KB/token → 一條 8K 序列就是 1 GB

預留 vs 實際使用

用到 25%

浪費的 60–80%

放得下的條數直接被砍到 1/4 → B 上不去

記憶體碎片化不是「記憶體問題」，是 batch size 問題；batch size 就是 GPU 利用率。

1960 年代的虛擬記憶體分頁機制搬到 KV cache 上。vLLM 的 PagedAttention 讓它出名，但 SGLang 底下同樣是分頁式記憶體池。

邏輯序列（使用者看到的）

tok 0–15

tok 16–31

tok 32–47

block table

0 → #47

1 → #12

2 → #89

實體 HBM block pool（16 token / block，可不連續）

■ 請求 A　■ 請求 B　■ 請求 C　■ free pool

浪費 60–80% → < 4%

用完才要、不用連續

請求結束立刻歸還

block 可跨請求共享 ←關鍵

這一層兩家沒有分歧——所以「RadixAttention vs PagedAttention」是把兩層混為一談。分歧在下一頁：block 放好之後，怎麼被找到。

同一個問題：「這個新請求的前綴，之前算過嗎？算到哪？」——兩家用了完全不同的資料結構。

共用 system prompt

對話 A

對話 B

→

blk1 (16 tok)

blk2 (16 tok)

對比②b 排程：主動提高命中率 vs 被動命中

有了索引還不夠——請求「以什麼順序進來」也會改變命中率。這是兩家差最多的一點。

同樣三個請求，順序不同，命中率就不同

亂序

A（前綴 X）

B（前綴 Y）

C（前綴 X）

排過

A（前綴 X）

C（前綴 X）命中！

B（前綴 Y）

↑ 亂序時 X 的快取可能已被 LRU 淘汰；排在一起就一定命中

SGLang

cache-aware 排程

· 主動把同前綴的請求排在一起送

· v0.4 起還有 cache-aware load balancer

· → 這是「引擎主動經營快取」的做法

vLLM

被動命中

· FCFS / priority 為主，不按內容重排

· 命中率取決於流量自然的到達順序

· → 引擎不猜工作負載，交給上層

zero-overhead scheduler

· 把 CPU 排程藏進「上一步的 GPU 執行時間」裡

· 排程與 GPU kernel 在時間上完全重疊

· v0.4 起導入，是它能撐大規模部署的關鍵

· 單一進程內把時序排好

vLLM

多進程 + async 排程

· EngineCore 獨立進程只跑排程 + 執行

· tokenize / 多模態前處理 / 串流輸出各自重疊

· async scheduling：下一步決策與本步執行重疊

· 用進程邊界隔開，工程上較易維護

為什麼值得講這一頁

帶走三句話

1

每個機制都是被一個具體痛點逼出來的

DSL 因為程式難平行、前綴複用因為程式製造了大量共享前綴、FSM 因為 agent 需要能解析的輸出、CPU 優化因為前三個解完 GPU 快到 CPU 跟不上。順著問題走，就不用背功能表。

2

兩家的差異幾乎都在「要不要替你猜工作負載」

SGLang 猜你會重複用前綴與語法（radix tree、cache-aware 排程、jump-forward），猜對了就贏很多；vLLM 不猜，把廣度與抽象做好（最多模型/硬體、可插拔後端）。共同地基（分頁 KV、continuous batching、XGrammar、CUDA Graph）兩家一致。

3

所以選型看流量長相，不看 benchmark 排名

前綴共用 >60%（agent／多輪／RAG）→ SGLang 的 TTFT 低 20–40%、結構化輸出快約 3×；請求彼此獨立 → 兩者差 <5%，就選硬體與模型支援更廣的那家。
