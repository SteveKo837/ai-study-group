warp 與 SIMT：用大量 thread 藏延遲

32 threads = 1 warp，一起執行同一指令（SIMT）。一個 SM 同時駐留很多 warp。

warp 0

warp 1

warp 2

warp 3

時間 →

橘＝在算　深＝等 HBM

一個 warp 在等 HBM（數百 cycle）時，排程器切到別的 warp 繼續算 → SM 始終有人在算。

藏延遲的前提：有夠多 warp、且頻寬餵得上——「大量平行」不是 GPU 的加分項，是它存在的前提。

04

餵飽一張卡要多少平行度？Amdahl 給天花板

H100 SXM 的「寬」

132 SM × 128 lane ≈ 16,896 條 lane + 528 tensor core

每條 lane 還要數十個 warp 待命藏延遲

→ 同時要有 10⁵ 量級的 thread 在飛

Amdahl's Law

加速上限 = 1 / ((1−p) + p/N)

p = 可平行比例，N = lane 數

p = 95%、N → ∞：最多也只有 20×

N 夠大之後，瓶頸只剩序列的 (1−p)

模型裡任何「序列相依」的部分，都是 p 的天花板——這句話 Part 3、Part 5 都會用到。

記憶體階層：每遠一站，慢一個數量級

層級約略頻寬誰管理備註
Register數十 TB/s編譯器晶片內最快
Shared memory / L1數十 TB/s程式可控tiling 的槓桿（Part 2）
L2 cache數 ~ 數十 TB/s硬體全 SM 共用
HBM（GPU 全域）2 ~ 4.8 TB/s程式配置A100~2 / H100~3.35 / H200~4.8
NVLink（GPU↔GPU）~900 GB/s（雙向）—比 PCIe 快一個量級
PCIe（Host↔Device）Gen4 ~32 / Gen5 ~64 GB/s—最常被跨越的瓶頸
CPU DRAM（DDR5）~50 ~ 100+ GB/sOS主機記憶體
NVMe SSD~3 ~ 7 GB/sOS資料集 / 權重來源

HBM 是 TB/s、PCIe 是 GB/s——差約 100×；瓶頸＝資料必經的「最慢那段路」（常是 PCIe）。能程式控制的只有 shared memory 與 register。

兩種「慢」：你被誰卡住？

Compute-bound

瓶頸：峰值 FLOPS（算得不夠快）

症狀：算力利用率高、加大 batch 也快不了

典型：大矩陣乘法、模型訓練

Memory-bound

瓶頸：記憶體頻寬（資料搬不夠快）

症狀：算力利用率低、加大 batch 吞吐會升

典型：自迴歸解碼、element-wise 運算

怎麼判斷在哪一邊？用一把尺：算術強度（下一頁）。

09

一把尺：算術強度 (Arithmetic Intensity)

AI = 完成運算的 FLOPs ÷ 需搬動的 Bytes

單位：FLOPs / Byte —— 每搬 1 個位元組，能換到幾次浮點運算

AI 高 → compute-bound

每搬一點資料就做很多運算。例：大方陣 GEMM，AI ≈ 數百。

AI 低 → memory-bound

大多時間在等資料。例：矩陣×向量 GEMV，AI ≈ 1–2（fp16）。

12

990 TFLOPS 哪來的？時脈 × 單元數 × 每 cycle 運算數

峰值算力 = 單元數 × 每 cycle 運算數 × 時脈 (clock)

同一顆 H100單元數每 cycle 運算數時脈= 峰值
CUDA core 路徑（fp32）132 SM × 128× 2（FMA：a×b+c 一次算 2 FLOPs）~2.0 GHz≈ 67 TFLOPS
Tensor core 路徑（bf16）132 SM × 4× ~1024（小矩陣乘加一口氣做完）~1.8 GHz≈ 990 TFLOPS

頻寬是同一條公式：HBM3 ≈ 5120-bit 介面 × ~5.2 Gb/s/pin ÷ 8 ≈ 3.35 TB/s ——「算力與頻寬都是：寬 × 時脈」。

兩條路徑時脈幾乎一樣、峰值差 ~15×——算力來自「每 cycle 運算數」不是 clock；GPU 時脈甚至比 CPU 低（Part 1）。

17

KV cache：省了重算，換來頻寬與容量壓力

是什麼

快取過去 token 的 Key / Value，讓每一步不必對整段序列重算 attention——是讓 decode 還能用的關鍵優化。

代價

隨序列長度線性增長

每步都要讀它 → 頻寬壓力

要存住它 → 容量壓力（限制 batch / context）

KV 大小 ≈ 2 × layers × heads × head_dim × seq_len × batch × dtype

context 越長 decode 每步要讀的越多 → 越 memory-bound。Part 5 的 GQA / Mamba 都是衝著它來的。

18

Batch 的魔法：throughput vs latency

為什麼加大 batch 有用

batch=1：讀一次權重只服務一個請求 → 浪費

batch=N：同一次權重讀取服務 N 個請求

→ 吞吐近乎線性升、單步延遲幾乎不變

直到變 compute-bound 或 KV cache 裝不下

吞吐升、但「單一請求的延遲」沒變快——batch 是攤平權重讀取，不是加速。

TPU：另一條路 — systolic array（脈動陣列）

設計哲學：GEMM 專用到極致

MXU = 128×128 個 MAC 排成陣列

weight-stationary：權重釘在格子裡，資料流過去

沒有 warp、沒有動態排程——資料跟著 clock 齊步走

XLA 編譯器把整個計算圖先排好（靜態）

Transformer 在 TPU 上

訓練 / prefill 的大 GEMM = 甜蜜點，利用率高

decode 的小 GEMV 一樣餵不滿陣列 → 一樣 memory-bound

bf16 就是 TPU 帶進主流的（模型→硬體→模型的迴圈）

也配 HBM——頻寬牆跨硬體成立

GPU 用「上萬 lane + 動態排程」、TPU 用「固定資料流 + 編譯器」——兩條路都是為 GEMM 而生；瓶頸物理相同。下一頁看第三條路 Groq。

Groq LPU：KV 塞不下晶片 → 乾脆把記憶體全做成 SRAM

GPU / TPU 的 decode 痛點

HBM

權重+KV ~GB

L2 50MB

tensor

core

Groq 的答案：砍掉 HBM、全用 SRAM

記憶體牆是物理：GPU 在 HBM 上想辦法（FlashAttention 省 S、GQA 省 KV）、Groq 直接換掉 HBM——三條路都在繞同一道牆。互動地圖硬體層可切 GPU/TPU/Groq。

紙上 FLOPs ÷ 8–9（9C² → 9C + C²）

但 depthwise 每 byte 只做幾次運算 → AI 個位數、memory-bound

channel 軸被拆散 → 餵不滿 tensor core

它的目標硬體本來就是手機 CPU

ConvNeXt（2022）：反向操作

用 transformer 時代配方重設計 ResNet

敢用 7×7 大 kernel：FLOPs 多但平行度好、AI 高

GPU 上「多而齊」常勝過「少而碎」

紙上 FLOPs 是 CPU 思維；GPU 上要問 bytes 與平行度——和 decode memory-bound 同一個道理。

1

先問 compute-bound 還是 memory-bound——用算術強度那把尺。

模型與硬體互相塑造——看新架構先問三個硬體問題。

平行軸？每 byte 幾次運算？序列鏈多長？CNN → Transformer → 混合，就是輪流補洞。
