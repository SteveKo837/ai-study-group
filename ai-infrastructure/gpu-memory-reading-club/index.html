為什麼同一個模型，換個搬資料的方式就差十倍？

給會寫 PyTorch、但沒碰過 CUDA 與計算機組織的 data science／ML 工程師。從一張 GPU 的記憶體階層出發，一路走到上百張卡的推論叢集：每一堂都在回答「資料在哪、怎麼搬、誰在等誰」。

一把尺：Roofline算術強度 = FLOPs ÷ 搬動的 Bytes。低於 ridge point 就是 memory-bound，換更強的算力也沒用。
一張地圖：記憶體階層每離運算單元遠一站就慢一個數量級。瓶頸永遠是資料必經的最慢那段路。

四堂課

同一個敵人（decode 是 memory-bound），四個高度：硬體的尺 → 單卡到多卡 → 單機引擎 → 從模型架構到一整排機櫃。照順序讀，每一堂都接住上一堂留下的問題。

1

硬體 × Transformer一張卡本身

roofline、記憶體階層、GPU 的 SM／warp／tensor core，把 Transformer 放上機器：訓練、prefill、decode 各被誰卡住。最後看模型與硬體怎麼互相塑造（CNN → Transformer → 混合架構、TPU、Groq）。

Transformer × GPU一張卡 → 多張卡

玩具 Transformer 逐個 block 對到 GPU 單元，看哪裡吃 tensor core、哪裡 memory-bound。一張卡裝不下之後：DP／TP／PP／EP 怎麼切，NVLink、NVSwitch、InfiniBand 各自扛哪一段。

推論引擎會撞到的問題①–④：程式難平行、前綴被重算、結構化輸出太慢、CPU 排程變瓶頸。每個問題都對照兩家的寫法（radix tree vs 雜湊鏈、jump-forward、zero-overhead scheduler）。

最終章：從模型到機櫃模型內部 → 全部組裝起來

前半先認識要搬上機櫃的模型：decode 怎麼一次吐一個字、MoE 怎麼挑專家，再用五個旋鈕（壓 KV、少算、少看、一次多產、降精度）過一遍 DeepSeek／Kimi／MiniMax／Qwen／GLM 的思路。後半跟著一個請求穿過 SGLang 96×H100 叢集：四種資料 × 四條路，真瓶頸是 scale-up 域的大小。
